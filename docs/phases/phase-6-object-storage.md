# Phase 6 — Object Storage for Large Values

## Goal

Allow task inputs and results larger than the inline limit by storing them in an S3-compatible object store, with only a checksummed reference in PostgreSQL.

Until this phase, a value over the inline limit is rejected with `value_too_large`.

## Contract

- Values at or under `TASKWIRE_INLINE_LIMIT_BYTES` (default 256 KiB) stay in the backend. Larger values are uploaded and replaced by a reference.
- A reference is `{store, key, size, sha256, codec}`. Objects are immutable; keys are generated by Taskwire and never chosen by the caller.
- The client uploads inputs before `submit`. The worker's task process downloads inputs and uploads results. Clients and workers talk to the object store directly; no Taskwire process proxies bytes.
- Every download verifies size and SHA-256. A mismatch or a missing object fails the task with code `storage_consistency`, which is not retryable.
- An upload that succeeds but whose database write does not commit leaves an orphan. Orphans are harmless and are removed by the sweeper.

## Backends

| Backend | Use |
|---|---|
| `s3` | Any S3-compatible service; installed by the `taskwire[s3]` extra |
| `filesystem` | Local development and tests only; requires a path shared by all processes |

Configuration is by environment variable: `TASKWIRE_OBJECT_STORE`, `TASKWIRE_S3_BUCKET`, `TASKWIRE_S3_PREFIX`, `TASKWIRE_S3_ENDPOINT_URL`. Credentials come from the standard provider chain, so workload identity on Kubernetes works without static keys.

A hard ceiling, `TASKWIRE_MAX_VALUE_BYTES`, bounds any single value.

## Garbage collection

- `Backend.purge` already returns the object references of the tasks it removes. The controller deletes those objects after the purge has taken effect.
- A sweeper lists objects under the prefix older than the retention period plus a safety margin and deletes any that no task row references.
- Deletes are idempotent and retried. A failure to delete never blocks retention of database rows.
- A bucket lifecycle rule is documented as a backstop.

## Metrics

Added to the worker and controller: object bytes uploaded and downloaded, object operation duration by operation, checksum failures, and objects deleted by the sweeper.

## Required tests

Run against an S3-compatible test server.

- Values just under, at, and over the inline limit take the right path; round trip is byte-exact.
- Corrupted and missing objects fail the task with `storage_consistency` and are not retried.
- A crash between upload and submit leaves an orphan that the sweeper removes; a referenced object is never removed.
- Retention deletes the objects of purged rows.
- Object store outage: uploads fail with a retryable error; running tasks retry within their lease; no database row references a missing object.
- Throughput and memory: a value near the ceiling is streamed, not held twice in memory.

## Exit gate

Large inputs and results work end to end on Kubernetes with an S3-compatible store, integrity failures are surfaced and not retried, and a sustained run leaves no unreferenced objects after the sweep window.
